## L2 的主要风险与处理

### 风险 1：多标签打破 L1 的"单编辑器"假设

L1 的渲染层到处隐式引用一个全局 `editor`。L2 引入多标签后，最大风险是
**隐藏/非活动编辑器持有过期内容**——这正是 L1 踩过的丢内容 bug（当时是隐藏的 textarea）。

**处理方式：内核按需挂载。** 只有活动会话持有 EditorApi 与 DOM，
切走时立刻序列化内容并销毁内核。由此得到三个确定收益：

1. 标签数不影响内存（打开 50 个文件不会创建 50 个 contenteditable）
2. 内核与"当前可见文档"强绑定，**结构上不可能**存在隐藏编辑器读到过期数据
3. 切标签只是"序列化旧会话 → 装载新会话"，无状态共享

**代价：切标签会丢失每个会话独立的撤销栈。** 这是明确的取舍。
若要保留各自撤销栈，只需把 `editor` 从单例改为 `Map<id, EditorApi>`，
其余逻辑无需改动——这是"markdown 为权威内容"带来的好处。

### 风险 2：文件系统能力的越界

L2 把目录遍历、文件增删改交给渲染层，这是攻击面扩大。
**处理方式：全部文件操作在主进程做路径校验**（`assertInsideWorkspace`），
渲染层即使被注入也无法读写工作区之外的位置。此项有专门断言覆盖。

### 风险 3：搜索是纯磁盘操作，可能拖死 UI

**处理方式：三重上限 + ripgrep 优先。**
深度 12 层 / 5000 个条目 / 单文件 8MB / 500 条结果上限；
优先用 ripgrep（已处理各种边界且极快），不可用时退化为纯 Node 遍历，
两条路径返回同构结果，上层无需分支。

另加**请求序号机制**：用户快速输入时先发的请求可能后返回，
只接受最新序号的结果，否则会看到与当前关键词不匹配的旧结果。

### 一个值得记录的实现细节

L1 的文档内查找是"在 markdown 字符串里 indexOf"，在所见即所得模式下会错位——
因为 **markdown 字符偏移与 ProseMirror 文档位置没有对应关系**
（`**` 占 2 个字符但 0 个文档位置，列表缩进、引用前缀同理）。

L2 改为遍历文档文本节点建立"字符偏移 → 文档位置"映射。
这个映射是查找功能的正确性基础，也是后续"全局搜索结果精确定位"的前提。

## 自检断言演进

| 级别 | 断言数 | 覆盖重点 |
|---|---|---|
| L0 | 13 | 沙箱通路、编解码往返、原子写、脏标记 |
| L1 | 20 | markdown 逐字往返、输入规则、块级/行内命令、撤销栈 |
| L2 | 30 | 多标签隔离、工作区树/搜索/文件操作、大纲、查找、越界防护 |

**每级都保留前级断言**，因此任何一级的功能退化都会立刻暴露——
L2 开发中"L1 内核往返仍成立"这条断言就立刻抓到了期望值错误。

## 已知限制

- 撤销栈按标签独立丢失（见风险 1 的取舍说明）
- 删除文件走原生 `window.confirm`，视觉上不统一 → L5 换成自定义非阻塞确认框
- 文件树只监听工作区根目录一层，深层改动需手动刷新（⇧⌘R）
- 大纲跳转定位到标题内部，未做"滚动到视口中央"的体验优化
- 表格、公式、图表、图片、任务列表 → L3
- 导出 → L4

## 打包：从 247 MB 到 95 MB

第一次打包产出 247 MB，且 asar 里躺着一整棵 `node_modules`。根因是
**依赖分类错误**：所有第三方包（ProseMirror、KaTeX、highlight.js…）都被列在
`dependencies`，但它们是 **Vite 的构建期输入**——运行时一个都不需要，
因为 Vite 已把它们打进 renderer bundle。

修正后 `dependencies` 只剩 `electron-updater`（主进程真的在运行时 require 它），
asar 从约 40 MB 降到 **2.6 MB**。

最终的体积构成：

| 部分 | 体积 |
|---|---|
| Electron 框架 | 233 MB |
| 应用代码 + 资源（asar） | 2.6 MB |
| **合计（未压缩）** | **236 MB** |
| **zip（可分发）** | **95 MB** |

这 233 MB 是 Electron 的固有成本，也正是当初预算里 Tauri 方案省下的那部分。
当初的取舍（选 Electron 省 2.7 M token，代价是安装包约 120 MB）在这里得到验证。

## 性能优化：逐键重算是大文档的真实瓶颈

**问题**：每次按键都会全文扫描三遍——字数统计、标题遍历、markdown 重新渲染。
一万行的文档上这是肉眼可见的输入延迟。

**处理**：把这些"不需要逐键精度"的计算合并到一次延迟执行
（`EXPENSIVE_REFRESH_DELAY_MS = 120`）。连续的即时反馈（脏标记、标签栏、
工具栏高亮）仍然逐键更新。

实测结果：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 连续输入 20 次 | 约 40+ 次重算 | **0 次**（输入期间） |
| 停顿后 | — | **1 次** |
| 统计准确性 | — | ✅ 断言校验（32 字符与实际一致） |
| 装载文档 | — | 仍立即刷新（用户在等结果） |

**为什么把刷新次数做成可观测量**：没有它，性能回归只能靠人工手感发现。
`getExpensiveRefreshCount()` 让自检可以断言"合并确实生效"，
而不只是"功能还正常"。

## 自动更新：三个约束

| 约束 | 原因 |
|---|---|
| **开发期完全禁用** | 未打包时 electron-updater 会去读不存在的 `app-update.yml` 并报错 |
| **绝不打扰用户** | 检查到新版不弹窗、不阻塞启动，只提示；由用户决定何时下载与重启。编辑器最忌"写作时被重启打断" |
| **失败静默** | 更新服务器不可达（离线、内网、服务未部署）是最常见情况，不能因此报错 |

同时这也是对本项目"零运行时依赖"设计的一次**有意修正**：
electron-updater 必须在运行时可用，因此它理应在 `dependencies`。
把它塞进 `devDependencies` 会让打包后的应用缺少更新能力——
这是"为了让依赖表好看"而引入的真实缺陷。

## 打包产物暴露的缺陷：更新配置缺失

这是本阶段唯一一个**只在打包产物上出现**的缺陷，也是"必须测打包产物"的最好例证。

| 项 | 内容 |
|---|---|
| 现象 | 打包后的自检报 `更新检查 — error / ENOENT: no such file or directory, open '.../app-update.yml'` |
| 根因 | 打包后 `app.isPackaged` 为 true，代码会加载 electron-updater；而 `dir` 目标**不生成** `app-update.yml`（只有 dmg/zip/nsis 等可发布目标才生成），模块初始化时读文件失败 |
| 为什么开发态发现不了 | 开发态 `app.isPackaged` 为 false，根本不走这段代码 |
| 修复 | 加载前先检查配置文件是否存在；缺失时归入 `unavailable` 并给出可读原因：<br>「该构建未包含更新配置（需使用 dmg / zip 等可发布目标打包）」 |

**修复后同一条断言在三种环境下都成立**：开发态 → unavailable；
`dir` 打包 → unavailable（带原因）；zip/dmg 打包 → 正常检查。

这类问题的通用教训：**把原始的系统错误直接抛给用户，等于没有处理错误。**
`ENOENT` 对用户毫无意义，而"该构建未包含更新配置"直接告诉了他该怎么做。

### 图标为什么用脚本生成

图标是**二进制资产**：无法代码评审看清内容、无法 diff、三平台还要 icns/ico/png
三种格式与多档尺寸（手工维护极易缺档导致打包失败）。
本项目的图标是简单几何形状，用脚本表达比二进制更可读、可改。

### i18n 为什么用函数式消息而非插值模板

`messages.status.openedFile` 这类结构化访问有编译期检查；
改成 `t('status.openedFile')` 会丢掉它，键名拼错只能等运行时暴露。
确实需要变量时用 `format(template, values)` 显式处理。

## 人工验收发现的 4 个 UI 缺陷

这一轮缺陷有一个共同点：**它们全都"功能正常"**——
所有数据流断言都通过，但界面呈现是错的。自动化断言覆盖了"数据对不对"，
却没有人检查"用户看到什么"。

| # | 现象 | 根因 | 类别 |
|---|---|---|---|
| 1 | 文件树下出现两行"未打开文件夹" | 路径栏与文件树空状态**重复表达同一件事** | 信息重复 |
| 2 | 工具栏最右侧两个按钮空白 | 加 i18n 标注时把 `HTML`/`PDF` 文字删掉了；这两个按钮只有 `data-i18n-title`（title 不显示为内容），于是没人填回文字 | **我的 bug** |
| 3 | 查找框压住工具栏 | `position: fixed; top: 52px` 隐含假设"工具栏高度恰好 52px" | 硬编码假设 |
| 4 | 两个图标看不懂 | `▤` / `▦` 是无语义的方框字符，且字形随字体变化 | 语义缺失 |

### 缺陷 3 的修复经历了两轮，值得记录

第一次修复：把查找框从 `body` 移到内容区，用 `position: absolute`。
**结果它压住了标签栏**——因为内容区包含标签栏，`top: 8px` 正好落在标签上。

第二次才是对的：把它锚进**编辑区**内部。

三次尝试的区别不在数值，而在**锚在哪一层容器**：
`body`（依赖工具栏高度）→ 内容区（压住标签栏）→ 编辑区（上方确实没有其它 UI）。
教训是：**遇到"定位被其它元素压住"，先问锚点层级对不对，而不是调 `top` 的值。**

### 缺陷 2 引出的新断言形式

这个 bug 单看代码很难发现——它需要"把每个按钮都当成可能为空"来审查。
因此新增了一条**结构性断言**，而不是只修好那两个按钮：

```
✓ 工具栏按钮均有可见内容或图标 — 共 28 个按钮
```

判据是：每个按钮必须有非空文本 **或** 一个 `<svg>` 子元素。
同类断言还有"图标按钮均含 SVG"（防止类名加了但图标忘了）。

**这类断言的价值在于它覆盖"未来的按钮"，而不只是"已知出错的按钮"。**

### 顺带修正的一处设计问题

表格的行/列操作按钮原先只是**禁用**（灰显），但它们仍占着工具栏宽度、持续分散注意力。
改为**只在光标位于表格内时出现**——"插入表格"始终保留，它是进入表格的唯一入口。

这同时缓解了工具栏拥挤：28 个按钮里最多同时只显示 24 个。

## 人工验收发现的缺陷：查找框只能输入一个字母

用户报告："输入一个字母，光标就弹走了，想搜 docker 只能输入 d"。

### 根因

查找框每次 `input` 都会调用 `focusCurrentMatch()` 去显示当前匹配，
而它在两条模式下都会**把焦点交给编辑区**：

| 模式 | 抢焦点的调用 |
|---|---|
| 所见即所得 | `selectRange()` 内部的 `editor.view.focus()` |
| 源码 | `dom.rawEditor.focus()` |

于是第一个字符输入后焦点就离开了查找框，第二个字符落到了编辑器里。

### 修复

给 `selectRange` 增加**显式的 `focus` 选项**（默认 `true`），
查找调用时传 `{ focus: false }`；源码模式改为 `revealRangeInTextarea()`
——只设置选区并按行高换算滚动位置，不调用 `focus()`。

**为什么是加选项而不是直接去掉 `focus()`**：
"跳到某处"这个动作在用户**主动点击**时理应带走焦点（例如点击工作区搜索结果），
只有"每输入一个字符就调用一次"的场景才不能抢。把这个差异显式写在调用点上，
比让函数内部隐式决定更不容易再错。

非聚焦的 textarea 不会自动滚动，因此源码模式必须手动换算 `scrollTop`，
否则匹配项在视口外时用户看不到。

### 断言先证明"能抓住 bug"，再证明"修好了"

这条断言没有只验证修复后的行为，而是**先用有缺陷的代码跑了一遍**，
确认它确实会失败：

```
修复前: ✗ 在第 "o" 个字符处失去焦点，实际输入 "d"
修复后: ✓ 完整输入 "docker"
```

失败信息精确复现了用户的报告（只能到 "d"）。
**一条从未失败过的断言，无法证明它有检测能力。**

### 同类问题审计

顺带审计了渲染层全部 **26 处 `.focus()` 调用**，确认只有 `selectRange`
这一处会从"用户正在输入的控件"里抢走焦点；其余 25 处都是用户主动操作
（切标签、开查找、点工具栏、点大纲、点搜索结果）之后的合理归位。

## 人工验收发现的缺陷：查找跳转无效（ProseMirror 的设计约束）

用户报告："按 Enter 和点击上下按钮，都不会跳转到匹配内容的地方。"

### 根因：ProseMirror 在视图未聚焦时拒绝写入选区

修好"只能输入一个字母"之后，跳转仍然无效。查 ProseMirror 源码找到了根本原因：

```js
function editorOwnsSelection(view) {
  return view.editable ? view.hasFocus() : ...
}

function selectionToDOM(view, force) {
  ...
  if (!editorOwnsSelection(view)) return    // ← 提前返回
}
```

留给查找场景的是两个**互相冲突**的约束：

| 约束 | 来源 |
|---|---|
| 焦点必须留在查找框 | 否则用户无法连续输入（上一个缺陷） |
| 选区必须写进 DOM 才能看见高亮 | ProseMirror 的 `editorOwnsSelection` 守卫 |

焦点同时只能在一处，**这个矛盾无法在"用选区显示匹配"的框架内解决**。

### 解法：换掉显示机制

改用**装饰器（Decoration）高亮 + `coordsAtPos` 手动滚动**：

| 机制 | 是否依赖焦点 |
|---|---|
| DOM 选区 | 是（被守卫拦住） |
| **装饰器** | **否**——纯渲染层标注 |
| `tr.scrollIntoView()` | 是（依赖 DOM 选区） |
| **`coordsAtPos` + `scrollTop`** | **否**——基于 DOM 布局计算 |

这本来也是成熟编辑器的通用做法。附带收益：可以**同时高亮所有匹配**并把当前项单独强调，
而选区只能表达一个位置——用户现在能一眼看到关键词在全文的分布。

### 断言设计：不能只看查找框自己的计数

用户报告的现象是"计数在动，内容不动"。因此断言必须检查**编辑器里的显示**：

| 断言 | 判据 |
|---|---|
| 查找在编辑器中渲染全部匹配高亮 | `.search-hit` 数量 |
| 当前匹配项唯一标出 | `.search-hit--current` 数量为 1 |
| Enter 步进使当前高亮在屏幕上的位置改变 | `getBoundingClientRect().top` 变化 |
| **步进到视口外的匹配时触发滚动** | `scrollTop` 变化 |

最后一条的写法值得记录：**必须一直步进到滚动真的发生**，而不是只走一步。
前几个匹配就在文档顶部，此时"把匹配放到视口上方三分之一处"计算结果本就为 0，
不滚动是**正确行为**——只走一步就断言会在匹配靠前时误报失败。

（调试这条时我一度以为滚动代码有问题，是诊断信息里
`scrollHeight: 4872 / clientHeight: 646 / offset: 105.56 / appliedScrollTop: 0`
说明容器找对了、内容可滚动、匹配就在顶部，才定位到是测试选错了匹配项。）

## 人工验收发现的缺陷：点击搜索结果后高亮"跑到别处"

用户报告："搜索，点击搜索结果，高亮显示，没有显示搜索结果，而是其他地方高亮显示了。"

这里藏着**两个独立**的问题，靠肉眼观察会把它们混为一谈。

### 问题一：行内代码与选区用了完全相同的背景色

```css
.typeflow-editor code        { background: var(--accent-soft); }
.typeflow-editor ::selection { background: var(--accent-soft); }   /* ← 同一个值 */
```

用户看到文档里某处**行内代码**（`docker exec -it mycentos`）带着浅蓝底色，
自然理解为"高亮跑到那里去了"。**这不是定位错，是本该可区分的两种视觉状态无法区分。**

修复：拆成两个语义明确的变量——行内代码用中性灰（读作"代码"），
选区用带透明度的强调蓝（读作"被选中"）。

断言写成"两个变量取值不同"而非比较具体颜色：前者表达设计意图
（必须可区分），后者一改配色就失效。

### 问题二：选区在下一帧被静默清空（真正难查的那个）

把问题一解决后，断言仍然失败。用**两阶段读取**定位到了机制：

```
立即="docker ps -a # TARGET-LINE-MARKER"   ← 选中完全正确
一帧后=""                                   ← 一帧后选区消失
```

根因在代码块 NodeView 的染色实现：

| 步骤 | 发生了什么 |
|---|---|
| 1 | `paint()` 用 `replaceChildren()` 重建 `contentDOM` 的子节点 |
| 2 | 承载浏览器选区的 DOM 节点被**销毁**，浏览器把选区折叠 |
| 3 | ProseMirror 的 DOM 观察器读到这个折叠的选区 |
| 4 | 它把这个结果**反向覆盖回 state**，刚设好的选区就没了 |

而 `paint()` 被安排在下一帧执行（那是另一个修复的代价，见 L3 文档），
于是"设选区"与"重建 DOM"恰好形成这个顺序——**任何设完选区就渲染的场景都会中招**。

修复：重建后立刻把 state 的选区写回 DOM。`view.focus()` 内部正是
"停观察 → 写选区 → 恢复观察"，调用它可避免观察器读到中间状态。

但要加两个守卫，否则会重新引入此前修过的抢焦点缺陷：

```ts
if (selectionInside && this.view.hasFocus()) this.view.focus()
```

- `selectionInside`：选区不在本块内时，重建 DOM 不会伤到选区
- `hasFocus()`：焦点不在编辑区时（例如在查找框里输入），绝不能去 focus

### 这个缺陷为什么难查

- 修复前的状态是"选区一闪即消失"，肉眼几乎看不见
- 与实际存在的"行内代码底色"叠加后，现象被解释成"高亮在别处"
- 只有**分段读取中间状态**（立即 vs 一帧后）才能区分"从未选中"与"选中后被清空"

如果只写"点击后应该选中目标文本"并按最终状态断言，会得到
"选中为空"这个**正确但无信息量**的失败，无法指向任何机制。

### 顺带补上的前提断言

定位仍依赖"用文件行号去编辑器 markdown 里取同一行"这一近似。
规范化会改变行数，漂移过大就会静默指向错误的行。因此补了一条

```
✓ 编辑器行号与文件行号量级一致（定位近似的前提） — 编辑器 327 行 / 文件第 326 行
```

它守住这个前提，让漂移在超限时立刻暴露，而不是等用户报告。

## 结构性重构：代码块 NodeView 不再改写 contentDOM

修完"高亮跑到别处"之后，同一根因又暴露了两个新缺陷，最终促成了这次重构。

### 三个缺陷，一个根因

| # | 症状 | 与根因的关系 |
|---|---|---|
| 15 | 设好的选区下一帧被清空 | `replaceChildren` 销毁了承载选区的 DOM 节点 |
| 16 | 定位标记渲染后消失 | 同一次 `replaceChildren` 把 ProseMirror 的装饰器 span 一并销毁 |
| — | （隐患）IME 组合态中断 | 每次重排都可能打断输入法 |

**代码块 NodeView 在重建 `contentDOM`**——这是根因。
先补的两次（重建后恢复选区、请求装饰器重绘）都只是打补丁：
装饰器重绘尤其失败，因为 ProseMirror 认为该 NodeView 的 DOM 未变而跳过重绘。

### 重构内容

把语法高亮从"NodeView 改写 DOM"改为"**装饰器**"：

| 部件 | 变化 |
|---|---|
| `code-languages.ts`（新） | 语言注册与 `computeHighlightRanges()`：返回**字符区间 + 类名**，而不是 HTML |
| `code-highlight.ts`（新） | 装饰器插件：扫描代码块、映射为文档位置、按内容缓存 |
| `code-block.ts`（重写） | 只管语言下拉框，**绝不触碰 `contentDOM`** |

`contentDOM` 创建一次之后终身不变，ProseMirror 完全掌控其内容。
选区、装饰器、IME 三者因此都不再被干扰——**这一整类问题消失**。

### 性能处理

高亮是纯计算，逐键全量重算会拖慢输入。因此按 `语言 + 代码内容` 缓存，
用 FIFO 淘汰并设上限 300 条。断言验证"重设相同内容后缓存不再增长"。

### 这次重构的教训

前两个缺陷各自被独立修复，但都只是缓解症状。**当同一个根因以不同症状反复出现时，
应该停下来消除根因，而不是继续打补丁。** 判断信号是"这次的修复方式与前一次高度相似"。

## 定位的地基换了：从行号改为行文本

修好渲染之后，定位仍然出错。诊断显示编辑器 329 行、搜索报告第 327 行——
**规范化造成的 2 行漂移，就足以让"按行号取行"落到完全不同的行上**
（`docker ps -a` 取成了 ` ```bash `），而且不会有任何报错。

直觉上"源码模式里行号就是文件行号"，但源码模式取的是**编辑器规范化后的 markdown**，
同样会漂移。

修复：**以行文本为权威**。

| 用途 | 依据 |
|---|---|
| 定位到哪一行 | 搜索返回的**完整行文本**（`lineText`） |
| 多次出现时选哪一处 | 行号比例估算的相对位置，仅作**消歧提示** |

为此在主进程的两条搜索路径（ripgrep 与 Node 回退）都补上了 `lineText` 字段。

### 断言据此拆成两个边界情况

滚动断言最初写的是"目标必须落在视口上半部"，结果**文档末尾的目标永远失败**。
诊断显示 `appliedScrollTop=6605` 而实际 `scrollTop=6205`——
被浏览器钳制到最大滚动值。目标在文档结尾时，没有足够内容垫在下面，
"放到上三分之一"在数学上不可能，**贴底是正确行为**。

因此断言拆成：

| 情况 | 期望 |
|---|---|
| 目标在文档中段 | 落在视口上半部（实测 top=292，视口中点 400） |
| 目标靠近文档结尾 | 允许贴底，但必须**已滚到底**且完全可见 |

**断言必须理解边界情况，否则会把正确行为判成缺陷。**

## 人工验收发现的缺陷：光标被困在代码块里

用户报告："光标一直在 `1111` 后面，我要在代码框下面写内容，光标移动不了。"

### 两个独立原因

**原因一：`stopEvent` 范围过宽，点击被丢弃。**

原来的实现是"`dom` 内、`contentDOM` 外一律拦截"：

```ts
stopEvent(event) {
  return this.dom.contains(event.target) && !this.contentDOM.contains(event.target)
}
```

点击 `<pre>` 的留白区域时它返回 true。而 ProseMirror 在 `eventBelongsToView` 里是这样处理的：

```js
for (let node = event.target; node != view.dom; node = node.parentNode)
  if (!node || node.nodeType == 11 || (node.pmViewDesc && node.pmViewDesc.stopEvent(event)))
    return false      // ← 任一节点拦截，整个事件被丢弃
```

**任一节点返回 true，整个事件就被丢弃**，ProseMirror 根本收不到——
因此无法把光标放到那里。修复是收窄到只拦截头部（语言下拉框需要原生行为）。

**原因二：代码块是文档最后一块时，没有任何出路。**

代码块后没有可落脚的位置：回车只在块内换行，方向键也移不出去。
修复是新增"退出代码块"手势：**⌘Enter**（Typora 同款）与**在块末尾按 ↓**，
两者都在块后补一个空段落并把光标放进去。

只在"光标在该块最末 + 该块之后没有其它块"时接管，其余情况交还默认行为。

### 断言的写法：为什么放弃了端到端鼠标测试

第一版断言用合成鼠标事件点击 `<pre>` 留白，检查选区是否移动。它**没有牙**——
因为判据里含有 `document.activeElement === 编辑器`，而编辑器本就聚焦，条件平凡成立。

第二版改成"选区位置必须变化"。它在修复后**仍然失败**（`选区 1 → 1`）。
诊断显示 `posAtCoords` 正常返回 `15/5`（代码块内），说明坐标映射没问题，
问题在于 ProseMirror 的 `LeftMouseDown` 需要完整的按下-抬起-移动序列，
**合成事件无法可靠驱动这条路径**。

第三版改为直接断言 ProseMirror 依赖的那个契约：

```
✓ 代码块留白不被 stopEvent 拦截 — pre 的 stopEvent=false
✓ 语言下拉框仍被 stopEvent 拦截 — select 的 stopEvent=true
```

通过 `pre.parentElement.pmViewDesc.stopEvent(event)` 取到 NodeView 并真实调用它。
精确、稳定，并且**已验证有牙**：换回旧的 `stopEvent` 会得到 `true` 并判失败。

**教训**：当端到端路径无法在测试环境中可靠驱动时，
退一步断言"该路径所依赖的契约"，比写一条看似端到端却平凡通过的断言更有价值。

## 人工验收发现的缺陷：表格多行被合并成一行

用户报告："这个表格，是不是有问题？"

### 根因：一行判空写错，导致所有行都进了表头

```ts
if (rows.length === 0) headerRow.push(...cells)   // ← 判断错误
else rows.push(cells)
```

`rows` 只在处理**非首行**时才增长。于是每一行都满足 `rows.length === 0`，
全部被追加进 `headerRow`——**一个 2 行 × 5 列的表格被写成单行 10 个单元格**，
解析回来就成了 1 行 × 10 列，行结构彻底丢失。

修复是用行下标判断：`if (rowIndex === 0) … else rows.push(cells)`。

### 为什么测试没抓到：一条恒真的断言

原来那条"表格 markdown 往返稳定"是这样写的：

```ts
const expectedTable = normalize(tableSource)
check('表格 markdown 往返稳定', normalize(expectedTable) === expectedTable)
```

**它验证的是 `normalize` 的幂等性，而不是往返稳定性**——
`normalize(normalize(x)) === normalize(x)` 恒为真，既不经过解析也不经过序列化。
所以它对表格序列化缺陷**零检测能力**，长期掩盖了这个 bug。

已改为走完整链路：`setMarkdown(source)` → `getMarkdown()` → 与源比较，
并补上"往返后行数不变""各行列数一致"两条结构性判据。

**这是本项目第二次遇到"断言没有检测能力"**（第一次是 L1 用空文档对比空文档）。
两次的共同点：断言的两个操作数来自同一个来源，因此恒等。
审查断言时值得自问一句：**"它在什么情况下会失败？"** 若答不上来，它就不是断言。

## 人工验收发现的缺陷：「插入表格」切换模式后永久变灰

用户报告："工具栏的表格按钮，添加一个以后，我切换源码和所见即所得以后，表格按钮变成灰色的了。"

### 根因：disabled 状态没有人负责收尾

`updateFormatButtons` 在源码模式下禁用**整组**按钮；回到所见即所得时：

```ts
for (const button of ... '[data-table]') {
  if (button.dataset.table !== 'insert') button.disabled = !inTable   // ← insert 被跳过
}
```

而「插入表格」按钮**既没有 `data-format`**（后面那个循环不处理它）、
**又被表格循环跳过**（只处理非 insert）。于是它被源码模式禁用后**永久保持灰色**——
切一次源码再切回来，就再也插不了表格。

修复：**先统一清除 disabled，再按需设置**，让每个分支只负责自己的规则，
不存在需要别人收尾的状态。

### 断言写法的调整

第一版断言只检查"光标是否仍在表格内"，它在修复前后都通过——**没有牙**。
因为 `setMarkdown` 对**内容相同**的文档做整篇替换时，ProseMirror 会把选区按 1:1 映射，
光标位置其实没变。也就是说我最初猜的根因（模式切换丢光标）是错的。

真正的判据是按钮的 `disabled` 状态：

```
✓ 切换模式后「插入表格」按钮恢复可用 — disabled=false
✓ 回所见即所得后格式组无残留禁用按钮 — 仍禁用 0 个
```

并已验证有牙：换回旧实现会得到 `disabled=true`、`仍禁用 1 个`。

**"灰色但可见"与"被隐藏"是两种不同状态，断言必须针对状态而非可见性。**

## 人工验收发现的缺陷：新建文件的输入行跑到整棵树末尾

用户报告："文件夹，点击在此新建文件，但新建文件没有出现在当前文件夹的最下面。"

### 根因：待处理输入行一律追加到列表末尾

```ts
// 待处理的新建/重命名输入行挂在列表末尾
if (pending) fragment.appendChild(buildPendingRow(pending))
```

`PendingAction` 里明明带着 `parentDirectory`，渲染时却完全没用它。
于是给**中段文件夹**新建文件时，输入行出现在整棵树的最下方（常常还在视口之外），
用户看起来就是"点了没反应"。

修复：由 `renderNode` 就地插入——

| 操作 | 插入位置 |
|---|---|
| 新建文件 / 文件夹 | 目标文件夹的**子项之后**（缩进深一级） |
| 重命名 | 被重命名项**之后** |

保留"末尾兜底"：若锚点没被渲染（文件夹被折叠、节点已消失），仍放到末尾并滚入视口，
否则用户点了按钮却没有反馈。

### 断言判断的是"插入位置"，而不是"文件是否出现在文件夹里"

用户点完按钮、**还没输入文件名**时就看不到输入行了，所以"文件是否进对了文件夹"
不是有效的判据。真正的判据是 DOM 顺序与缩进：

```
✓ 新建输入行位于目标文件夹的子项之后 — notes=3 beta=5 pending=6
✓ 新建输入行位于根级下一项之前（没跑到整棵树末尾） — pending=6 readme=12
✓ 新建输入行缩进比文件夹深一级 — 文件夹深度=0 输入行深度=1
```

"在当前文件夹的最下面"因此有了可检验的定义：
**位于该文件夹子项之后、根级下一项之前、缩进深一级。**

## 基础设施缺陷：构建门禁只校验了一个 bundle

排查上面那个缺陷时发现同一份源码报出过 **172、231、238 三个不同的断言数**。
差异不在测试代码，而在构建门禁：

```js
if (statSync('out/main/index.js').mtimeMs < newestSource) { /* 拒绝 */ }
```

electron-vite 依次构建 main → preload → **renderer**。门禁只看 `out/main/index.js`，
于是"main 是新的、renderer 是旧的"这种状态会被放行——自检跑在**过期的渲染层**上，
断言数量悄悄变少（少掉的正是新加的那些），却依然报告全绿。

修复：判据改为**最旧的产物必须新于最新的源码**。

```js
const oldestArtifact = Math.min(...artifactTimes)
if (oldestArtifact < newestSource) { /* 拒绝 */ }
```

收紧可行，因为三个 target 都设了 `emptyOutDir: true`，每次构建重写全部产物。
已验证有牙：把任意一个渲染层产物 `touch` 成旧时间，门禁立刻拦下并打印两侧时间。

### 为什么会漏这么久

宽判据的形状看起来"合理"——检查最关键的那个入口文件即可。
但它假设**三个 bundle 同时更新**，而这个假设没有被任何东西保证。
"断言数量变少却仍报告全绿"是最难察觉的一类失败：
**数字变了，结果没变。**

## 能力补齐：预览器支持表格

预览器是手写的逐行渲染器（预览是只读视图，不需要 ProseMirror 文档模型）。
它此前完全不认表格——管道表被当成普通段落输出成一堆竖线，商店截图里就是这样。

### 识别的关键是"下一行是分隔行"

只判断"当前行含竖线"不够，普通段落里也会出现 `a | b`。
真正的标志是下一行是分隔行（`| --- | :--: |`）。因此循环从 `for-of`
改为带下标的 `for`，表格分支可以消费多行。

新增能力：

| 能力 | 说明 |
|---|---|
| 列数与行数 | 列数以表头为准，数据行多出的丢弃、不足的补空 |
| 对齐 | `:---` / `:--:` / `---:` 映射为 `text-align` |
| 单元格行内语法 | 复用 `appendInline`，代码/加粗/链接在单元格内照常生效 |
| 转义竖线 | `\|` 保留为单元格内的字面字符，不当作列分隔符 |

### 顺带修掉一个数据丢失缺陷

写对齐断言时才发现：**对齐信息根本存不进文档**。

`table.ts` 里解析逻辑是完整的（`parseAlignment` 能读出 `:---` / `:--:` / `---:`），
但 schema 的 `cellAttributes` 是空的——对齐读出来后无处存放，
序列化时只能硬编码 `default`：

```ts
const alignments = headerRow.map(() => 'default')   // 无论原文是什么
```

后果是**静默数据丢失**：含 `:---:` 的表格打开再保存，对齐标记就没了。
预览只是把这个问题暴露出来的地方。

修复涉及三处：

| 环节 | 改动 |
|---|---|
| schema | `cellAttributes: { align: { default: null } }`，并包一层 `toDOM` 把属性渲染成行内样式 |
| 解析 | `buildTableNode` 按列写入 `attrs.align` |
| 序列化 | 从**表头单元格的属性**读回对齐，而不是硬编码 |

### 断言

```
✓ 预览把管道表渲染为 table 元素 — 1 个表格
✓ 预览表格列数与行数与源码一致 — th=3 td=6（期望 3 / 6）
✓ 预览表格按分隔行应用对齐 — [left,center,right]
✓ 预览表格单元格内的行内语法生效 — code="code" strong="粗体"
✓ 预览表格的转义竖线保留在单元格内 — "a|b"
✓ 围栏代码块内的表格样式文本不被解析 — 表格数=0
✓ 含竖线但无分隔行的段落不会被误判为表格 — 表格数=0 段落数=2
✓ 表头与数据行列数不一致时按表头列数渲染 — th=2 td=2
✓ 表格对齐在 markdown 往返后保留 — 分隔行="| :--- | :--: | ---: |"
```

已验证有牙：撤掉修复后分别为 `[默认,默认,默认]` 与 `| --- | --- | --- |`。

其中"含竖线但无分隔行"一条最初写成 `a | b\n没有分隔行` 并期望 2 个段落——
markdown 里单个换行属于**同一段落**（软换行），实际只有 1 段。
**那是测试写错，不是功能错**，已改用空行分隔。

## 人工验收发现的缺陷：英文界面残留中文 + 工具栏显示不全

用户报告："切换到英文以后，菜单栏还是有中文；菜单栏显示不全。"

### 缺陷一：英文界面里残留中文（工具栏，不是应用菜单）

先确认了一件容易误判的事：**应用菜单本来就会重建**。
`installRecentFilesMenu()` 名字像"只刷新最近文件子菜单"，内部却会调用
`Menu.setApplicationMenu(buildMenu())` 重建整份菜单——语言切换因此是同语言的。

我一度以为它只更新子菜单，额外加了一次 `installApplicationMenu()`，
结果同一次变更里把菜单构建了两遍。已在函数文档里写清这个行为，避免下一个人再误判。

真正残留中文的是**工具栏**，两处：

| 位置 | 内容 |
|---|---|
| 表格行列按钮 | `+行` `+列` `−行` `−列` `✕表`，连 `title` 一起硬编码 |
| 14 个按钮的 `title` 提示 | `一级标题 (⌥⌘1)`、`加粗 (⌘B)`、`无序列表`… |

这些都没有 `data-i18n*` 标注，因此中文界面看着完全正常，英文界面露出一片中文。

修复：全部接入 i18n（新增 `toolbar.*` 键，中英各一份），
并把 `index.html` 里三处初始中文（`0 个标签` / `0 字 · 0 行` / `默认`）
改成中性初始值，避免英文首屏闪出中文。

### 缺陷二：工具栏右侧被裁掉

之前为了保证"工具栏高度恒定"（查找框用固定 `top` 偏移），设了
`flex-wrap: nowrap` + `overflow-x: auto` + **隐藏滚动条**。

后果是窗口稍窄时右侧按钮被裁掉、且**看不出还能滚动**——用户以为按钮丢了。
英文标签更长（`Import theme`、`Compact`），更容易触发。

查找框后来已改为锚定编辑区内部，高度恒定的约束不复存在，因此改回
`flex-wrap: wrap`。工具栏会变高，但所有按钮始终可达。

### 断言的写法

| 断言 | 判据 |
|---|---|
| 英文界面工具栏无中文残留 | 逐个按钮检查 text 与 title 是否含 **CJK 字符** |
| 切换为英文后应用菜单同步重建 | 通过新增的 `api.smoke.menuLabels()` 读主进程菜单标签 |
| 工具栏按钮不被水平裁剪 | 每个按钮的 `offsetLeft + offsetWidth` 不超过工具栏 `clientWidth` |
| 工具栏无横向溢出 | `scrollWidth <= clientWidth` |

用"是否含 CJK"而不是逐个比对文案：这样**新增按钮忘记标注时也会被抓到**，
而不是只覆盖已知的那几个。

菜单断言是唯一能覆盖主进程菜单的手段（渲染层看不到菜单），
它是回归守卫而非本次修复的证明——已验证：撤掉 `installApplicationMenu()`
它依然通过，因为 `installRecentFilesMenu` 本来就会重建菜单。

### 顺带修掉的英文拼写问题

状态栏 `1 tabs` 是手工拼接的痕迹。已加单数键：英文显示 `1 tab`，
中文两种形式同值（无复数变化）。

## 人工验收发现的缺陷：英文界面在边角处仍残留中文

用户报告："工具栏没有了[中文]，但 Outline、Search 下面还有，另外窗口上也是中文：未命名。"

### 根因是同一类：模块在初始化时取一次 `messages()`

`data-i18n` 标注体系只能覆盖**静态 HTML**。由模块自绘的文案是在构造时取一次
`messages()` 的结果，语言切换后没人重取——中文界面完全正常，
只有切到英文才会暴露：

| 位置 | 表现 |
|---|---|
| 搜索面板空状态 | "未打开文件夹" |
| 搜索面板占位符 | "在工作区中搜索…" |
| 搜索面板 title | "区分大小写" |
| 大纲空状态 | "当前文档没有标题" |
| 大纲空标题占位 | "(空标题)" |
| 文件树新建默认名 | "未命名.md" / "新建文件夹" |
| 未命名标签标题 | "未命名"（会话创建时的快照） |
| 窗口标题 | "未命名 — TypeFlow"（主进程生成） |
| 搜索结果汇总 | "4 处匹配，分布在 2 个文件" |

修复分三类：

1. **模块自绘文案**：给 `outlineView` / `searchPanel` / `fileTree` 各加一个
   `refreshLocaleText()`，在 `changeLocale` 里统一调用。
   （文件树原先用"传入合成树重绘"刷新，会丢失展开状态与待处理输入行，已改掉。）
2. **会话标题**：新增 `store.retitleUntitled()`，语言切换后按新语言重建未命名标签标题。
3. **窗口标题**：标题由主进程生成、只在路径变化时重设，因此 `changeLocale`
   末尾主动重推一次 `setRepresentedFilePath`，让它用新语言重算。

### 断言从"工具栏"扩展到"整个界面外壳"

原来的断言只遍历 `.toolbar button`，因此漏掉了面板与窗口标题。
现在收敛为 `collectChromeText()`：遍历工具栏、侧栏标签、面板空状态、
侧栏输入框占位符、状态栏 chip，**刻意排除**文档内容、预览区与文件名
（那是用户自己的文本，含中文完全正常）。

共检查 66 处文案。并且新增了窗口标题断言——通过扩展 `api.smoke.menuLabels()`
让主进程一并返回 `windowTitle`，这是渲染层看不到的部分。

已验证有牙：撤掉搜索面板的状态刷新，断言立刻报
`空状态="未打开文件夹" [locale=en-US]`。

### 为什么这类缺陷总是漏到用户手里

三次同类缺陷（文件树空状态、工具栏中文、面板文案）有同一个模式：
**缺陷只在"切换语言"这一条路径上可见，而每次开发都在中文下进行**。
单点修复不够，必须把断言从"我修的那一处"扩展到"这一类"——
`collectChromeText()` 的作用就是把"新增模块忘记接 i18n"也纳入检查范围。

## 人工验收发现的缺陷：语言菜单项只有第一次有效

用户报告："视图 → 切换界面语言，只有一次有效，后面点击无效。"

### 根因：拿 localStorage 快照当"当前语言"

```ts
async function cycleLocale(): Promise<void> {
  const index = SUPPORTED_LOCALES.indexOf(getCurrentLocale())   // 读 localStorage
  const next = SUPPORTED_LOCALES[(index + 1) % SUPPORTED_LOCALES.length]
  await changeLocale(next)
}
```

而 `localStorage[locale]` **只在启动时写入一次**——`changeLocale` 只更新内存里的
locale 和主进程偏好，从不回写 localStorage。

于是每次点击都算出同一个"下一个语言"：

```
第 1 次：zh-CN → en-US   ✓ 变了
第 2 次：zh-CN → en-US   ✗ 目标还是 en-US，看起来毫无反应
第 3 次：zh-CN → en-US   ✗ 同上
```

修复两处：

1. `cycleLocale` 改用**内存中的当前语言** `getLocale()`（i18n 模块的实时值）。
2. `changeLocale` 同时回写 localStorage，让快照与实际保持一致
   （否则"界面设置"里存的语言永远是启动时的那个）。

### 断言必须连续切三次

只切一次的断言对这个缺陷**毫无检测能力**——第一次本来就是好的。
判据是语言序列必须**交替**：

```
修复前: zh-CN → en-US → en-US → en-US   ✗
修复后: zh-CN → en-US → zh-CN → en-US   ✓
```

另有一条"反复切换后界面文案与当前语言一致"，防止"语言变了但界面没跟上"。

### 再记：支持 .txt 纯文本（2026-10-18 当日第二轮）

上表的 172 项 / 154 键是当日第一轮实测值，原样保留。第二轮把可打开类型从

  打开对话框过滤器、渲染层打开校验各写一份，并且已经漂移过：

- 目录树字段 `isMarkdown` 改名 `isText`；`.txt` 纳入工作区搜索

### 再记：支持 PDF / HTML / 图片只读查看（2026-10-18 当日第四轮）

需求原文是"要支持 pdf,html,和图片格式"，用户随即给出边界条件：
**"pdf,html,图片都只支持查看，不支持编辑，不能影响原有安全"**。
后半个条件是硬约束——安全基线那一节列的五条（沙箱、上下文隔离、无 `innerHTML`、
拒绝导航与新窗口、CSP）一条都不许放宽。实测数字：**断言 180 → 215（+35）、
156 → 163 键 × 2 语言**（净增 7 键，无改名）。

**CSP 一个字都没改**，三种格式各走一条不需要新指令的路：

| 格式 | 做法 | 为什么不需要放宽 CSP |
|---|---|---|
| PDF | pdf.js 6.4.299，**主线程"假 worker"**：先 `import` worker 模块再赋给 `globalThis.pdfjsWorker` | 不 `new Worker()`，因此不需要 `worker-src`；模块由打包器内联，不产生运行时脚本请求 |
| HTML | `DOMParser`（惰性、不执行）→ 标签/属性白名单重建 → `attachShadow` | 文档自带 `<style>` 的文本注入 shadow root 内部，沿用既有 `style-src 'unsafe-inline'`，且出不了子树 |
| 图片 | `<img src="file://…">` | `img-src` 早已放行 `file:`；SVG 同样走 `<img>`，因此不执行脚本、不发外部请求 |

否决过沙箱 `<iframe>` 方案：`sandbox` 不加 `allow-same-origin` 时是不透明 origin，
HTML 里引用的本地图片/CSS 会全部断；加上 `allow-same-origin` 又等于父级的 `file://`
同源，隔离作用归零，而且还得开 `frame-src`。

**只读做在模型层，不是"把按钮藏起来"。** `Session.kind === 'viewer'` 的会话：
`mount()` 第一行直接返回（永不挂内核，因此结构上不存在"隐藏编辑器读到 PDF 字节"）、
`saveSession()` 第一行拒绝（这是最后一道防线：查看会话没有权威文本，写盘等于清空用户文件）、
`isDirty` 恒为 false、命令总线用一张黑名单集中拦截 10 条命令（保存/另存为/两种导出/
查找/撤销/重做/插入表格/切模式/切布局），工具栏与格式按钮组同步禁用。
工作区全文搜索**不索引**只读对象——纳入只会给出点不动的死链接。

**cMap 与标准字体走白名单 IPC，不走 `fetch`。** `file://` 下没有可用 origin，
pdf.js 取 `cmaps/*.bcmap` 必然失败，而缺 cMap 会让使用预定义编码的中文 PDF **整页**渲染失败。
新增 `viewer:read-pdf-resource` 通道（`src/main/viewer-resources.ts`）：只放行
`cmaps/` 与 `standard_fonts/` 两个根、只接受单段文件名、单次 4 MB 上限；
自定义 `BinaryDataFactory` 让 worker 把取数请求转回主线程。构建期把这两个目录拷进
`out/renderer/pdfjs/`，因为打包后 `resourceRoot()` 与开发期不同——**这两条断言是专为产物加的**，
`pack:verify` 会在产物上跑（实测 cMap 43,366 B、标准字体 17,597 B；
`../package.json`、`cmaps/../../main/index.js`、`wasm/qcms_bg.wasm` 均返回 `null`）。

新增 35 项断言的分布：查看会话模型与表面 5、只读约束 7、状态栏与编码指示 2、
HTML 净化 10、PDF 7、图片 1、目录树与搜索 3。

**本轮三个缺陷都只在运行时暴露，`typecheck` 与 `build` 全程绿灯。**

1. **`hashOriginal.toHex is not a function`**——每份 PDF 都整页失败。
   pdf.js 6.4 的默认构建调用 `Uint8Array.prototype.toHex/toBase64`（Chromium 140+ 才有），
   而 Electron 33 是 Chromium 130。抓到它的是"PDF 首页栅格化到 canvas（1704×2410）"
   这条断言：它检查 canvas 真的有像素尺寸，而不是检查"页面容器出现了"——
   容器出现了但 canvas 是 0×0，正好是这次失败的形态。
   修法是改用 `pdfjs-dist/legacy/build/*`（自带 polyfill，其 `.d.mts` 是
   `export * from "pdfjs-dist"`，类型完全一致）。没有选择手写原型垫片：
   那是替第三方库长期维护一层兼容代码。
2. **查找条浮在 PDF 上**——它锚在编辑区内部，查看表面接管后没人关它。
   现在进入查看表面主动 `closeFinder()`，并且 `closeFinder()` 对查看会话**跳过聚焦**：
   否则焦点会落到隐藏的 textarea 上，后续键盘输入写进上一个文档，
   那是"看不见却在改"的最坏形态。新增断言"切到查看会话时查找条自动关闭"。
3. **写进文档的一条限制是错的**——原先记的是"`useWasm: false` 因此 JPEG2000 / JBIG2 / ICC
   三类流不支持"。查 pdf.js 源码后发现前两类**有纯 JS 回退**：`WasmImage._getModule`
   在 `useWasm` 为假时走 `#getJsModule`，即 `import(`${wasmUrl}openjpeg_nowasm_fallback.js`)`。
   我们没给 `wasmUrl`，它拼出来是 `"null" + 文件名`，import 必然失败、解码器为 null，
   于是"不支持"这个结论看起来成立——**但原因是我们没投喂回退文件，不是 pdf.js 没有**。
   修法：构建期把两个 `*_nowasm_fallback.js`（合计 597,790 B）连同 4 份许可证拷进
   `out/renderer/pdfjs/wasm/`，新增 `viewer:pdf-wasm-url` 只返回该目录的 `file://` URL
   （`.wasm` 二进制刻意不拷：用不上，只会诱使后来者去放宽 CSP）。
   新增断言真的 `import` 这两个模块并检查 `typeof default === 'function'`，
   打包产物上实测 URL 是 asar 内路径且两个模块都加载成功。
   ICC 那部分结论不变，但理由要更正：qcms 只有 wasm 实现，且 `ColorSpace.setOptions`
   在 `useWorkerFetch` 为假时（自定义 `BinaryDataFactory` 就是这种情况）会直接关掉它，
   与 `useWasm` 取值无关。
   **教训**：把第三方库的限制写进文档前要去读它的源码，"我这边不生效"和"它不支持"是两件事。

**已知限制（记录，不粉饰）**：

- JPEG2000 / JBIG2 走纯 JS 解码器，比 wasm 慢；**含这类图像的 PDF 实际解码结果与耗时未实测**
  （手上没有样本），断言只证明模块可加载。
- ICC 色彩管理不生效（原因见上条第 3 点）：带 profile 的图像按设备空间渲染，颜色可能有偏差。
- 开发模式（`npm run dev`）下页面来自 dev server，跨源取不到 `file://` 的解码器模块，
  因此这两类图像只在构建产物里可用。
- PDF 单次读取上限 32 MB，沿用 `asset-io.ts` 的 `MAX_ASSET_BYTES`，超限提示"文档过大"。
- PDF 内嵌 JavaScript 不执行（未启用 scripting）。
- HTML 不加载任何远程资源：`http(s)` 只允许出现在 `href`（点击交系统浏览器），
  `src` 只接受 `file:` 与 `data:image/`。
- 第二轮遗留的 `fileAssociations` 仍未声明，Finder"打开方式"里看不到 TypeFlow。

### 再记：打开文件不再留下空白"未命名"标签（2026-10-18 当日第五轮）

用户截图报告：**"我已经打开了20261019.md，为什么前面还有一个未命名？"**

根因是两条各自合理、凑在一起就难看的规则：启动时先 `createUntitled()` 给一张白纸
（否则首屏什么都没有），而"打开文件"一律 `push` 一个新会话。
于是那张白纸永远留在标签条最左边，既没内容也没路径——
用户要么手动关它，要么以为"我打开一个文件却变成了两个标签"。

修法既不是"启动时不给白纸"（首屏空白更糟），也不是"打开后回头把白纸关掉"
（关闭流程要再跑一遍脏检查、焦点转移、相邻标签选择，全是额外状态），
而是**让打开行为就地改写那张白纸**：

| 情况 | 处理 |
|---|---|
| `blankUntitledActive()` 命中：活动会话是 `document`、`filePath === null`、`markdown` 与 `savedMarkdown` 都为空 | `createFromDocument` / `createViewer` 直接改写这个会话的字段（路径、标题、内容、编码、EOL；查看会话再改 `kind` 与 `viewerKind`），不新建标签 |
| 未命名但写过字 | 照旧新建标签，白纸留着 |
| 同一路径已有标签 | 照旧聚焦已有标签——这条判断排在替换之前，"一个文件一个标签"优先级更高 |

替换必须先 `unmountActive()` 再 `mount()`：内核实例与"当前可见文档"强绑定，
只改字段不重挂，编辑区里显示的仍是旧的空文档。
调用方无需改动——`openDocument()` / `openDocumentByPath()` / `openViewerByPath()`
本来就在建会话之后无条件调 `afterSessionActivated()`，替换路径同样会走到。

**替换的底线是不吃用户已经写下的东西**，所以判定条件里同时看内容与脏标记：
只有"未命名 + 空 + 没改过"才算白纸。这条底线单独有一条断言。

实测数字：**断言 215 → 217**，开发态与 `dir` 产物均 217/0；i18n 无新增键（改动不涉及文案）。
新增两条：

- `打开文档替换空白的未命名标签` — 详情 `标签 5 → 6（不替换会是 7）`。
  同时断言三件事：返回的会话 id 就是那张白纸的 id、它的 `filePath` 已变成打开的文件、
  标签总数只 +1（白纸本身已在计数里）。**只断言数量是不够的**：
  替换与不替换的差别是 +1 与 +2，得把这个差值写进详情里，失败时才看得懂。
- `有内容的未命名标签不被替换` — 详情 `标签 6 → 8`。断言新会话 id 与写过字的那个不同、
  写过字的会话仍然 `filePath === null` 且内容原样保留。

**写第二条断言时踩到一个坑，值得记**：最初只用 `store.commitActive('用户已经写下的内容')`
模拟"用户写过字"，断言失败——标签数量对得上（+2），但那个会话的内容变回了空字符串。
原因是 `commitActive` 只改会话模型里的字符串，而**内核里并没有这段文字**；
紧接着的 `unmountActive()` 按既定契约把内核内容序列化回会话
（这正是"markdown 是权威内容"的另一半），空内核于是覆盖了刚写进去的字符串。
改成先 `editor().setMarkdown(...)` 再 `commitActive(...)` 就对了。
**教训：自检里构造状态要走真实数据通路。** 绕过内核直接改模型，
测出来的不是用户会遇到的情形，失败时还会把矛头指向产品代码。

**另一处改动：更新检查断言放过网络层失败。** 原断言是 `checkResult.status !== 'error'`，
在 `dir` 产物上一直是绿的；但 `zip` / `dmg` 目标会**重新打包 `release/mac-arm64/`
并塞进 `app-update.yml`**，于是同一个 `.app` 的自检真的去请求
`https://updates.example.com/typeflow`，离线机器上必然
`error / net::ERR_NAME_NOT_RESOLVED`（本轮 `pack:verify --zip` 后连测 3 次，3 次都失败）。
现在的判据是"**只允许网络层失败**"：消息以 `net::` 开头、或含
`ERR_NAME_NOT_RESOLVED` / `ERR_INTERNET_DISCONNECTED` / `ENOTFOUND` / `EAI_AGAIN` /
`ECONNREFUSED` / `ETIMEDOUT` 之一即放过，其余 `error` 仍然判失败。
**没有改成"允许任何 error"**——那等于把 L5 修掉的缺陷（缺配置时把原始
`ENOENT … app-update.yml` 抛给用户）重新放回去；配置层失败的消息里必然带路径或 ENOENT，
与网络层失败在形态上可区分。
两种产物的期望形态因此是：`dir` → `unavailable`（"该构建未包含更新配置…"），
`zip` / `dmg` → 联网时正常返回、离线时 `error / net::…`。
顺带一个后果：交付验收用的是 `dir` 产物，菜单里的"检查更新"给出的是可读原因，
而不是一个 `net::` 错误码。

**一次没能复现的间歇失败（记录，不粉饰）。** 本轮 `pack:verify --zip` 的产物自检里，
"连续回车"组这两条失败过一次：

- `引用末尾第二次 Enter 退出到下方正文` —
  详情 `doc(blockquote(paragraph("引用回车测试")), paragraph("n"))`
- `退出引用后输入正文不带引用标记`（上一条的直接后果）

同组其余四条全部通过。其中 `退出引用后按钮取消高亮` 通过，说明**退出引用本身生效了**
（光标确实落在引用外），异常之处只是新段落里多出一个字符 `n`：
`doc.toString()` 对文本节点走 `JSON.stringify`，真换行会显示成带反斜杠的 `\n`
（同一次自检里 `code_block("11111\n22222\n3333\nqqqq")` 就是这么印的），
所以那是一个字面的字母 n，不是空白字符。
此后连跑 29 次产物自检（3 次单跑 + 14 次串行 + 12 次分三轮 4 路并发）**全部 217/0**，
未再复现。这次失败紧跟在打包与 zip 压缩之后，机器仍有负载，
而断言在第二次 Enter 之后只等两帧就读状态，因此**怀疑**与帧延迟期间某个被推迟的任务有关。
可核实的两点：产品代码里没有异步插入文本的路径（`insertText` / `autoInsert` /
标记规则全是同步 dispatch，主进程与 preload 里没有任何 `insertText`），
自检里也没有会打出字母 n 的地方（逐字符输入只有查找框那一处，输入的是 `docker`；
合成键盘事件只有 Enter 与 Backspace）。所以这只是怀疑，没有证据。
这条断言**没有放宽**：文档里凭空多出字符正是最该抓住的缺陷形态，
为了让自检变绿而容忍它是本末倒置。若再次复现，下一步是失败时连 `view.dom.innerHTML` 一起抓，
用来区分"内核状态里多了字符"与"DOM 被外部写入后被 DOMObserver 读回"。

**体积（2026-10-18 本轮重测）**：`app.asar` 10,604,554 B、应用包 243 MB；
分发产物 `TypeFlow-0.1.0-arm64-mac.zip` 102,421,094 B（22:06）、
`TypeFlow-0.1.0-arm64.dmg` 102,846,253 B（22:16）。
worker chunk 的文件名随构建变为 `pdf.worker-DvKV8mws.js`（2,348,879 B，字节数与上一轮相同），
pdf.js 主体仍是 `pdf-CJvgEmR7.js`（1,027,255 B），`out/renderer/pdfjs/` 3.1 MB。
`verify:all` 本轮三次实测 8.99 / 8.80 / 8.81 s（上一轮记的是 8.1 s，README 已按新值就地改正）。

### 再记：显示区滚动联动与工具栏显示区开关（2026-10-19 第六轮）

用户发来一张分屏截图，问了两件事：

1. **"左侧都移动到最底下编辑了，右侧还在最上面，这个是 bug？还是设计如此？"**
2. **"能不能加个图标，默认有编辑区和显示区，点击图标就只有编辑区，再点击显示编辑和显示区？"**

**第一问的答案是：不是 bug，是从未实现过。**
编辑区与显示区一直是两个各自 `overflow: auto` 的独立滚动容器，
仓库里没有任何把两者 `scrollTop` 关联起来的代码——既没有监听器，也没有比例或锚点计算。
这个区分很重要：退化要去查是哪次改动弄坏的，缺口只需要决定做不做、怎么做。

**用比例映射，不用按块对齐**（后者看起来更"正确"）：
显示区并不是把内核文档再渲染一遍，而是 `renderPreview()` 按 markdown **逐行**构造的
（空行也是 `<br>`，连续列表项合并进同一个 `.md-list`），
它的顶层元素与内核的块结构并不一一对应，按块对齐在多数文档上都会错排。
比例映射的代价是中部按高度近似，收益是两端严格对齐（滚到底就是到底），
且实现与文档结构完全解耦。

**回环防护用"吃掉自己写进去的值"，不用时间锁。**
双向联动天然成环（编辑区 → 显示区 → 编辑区 …）。常见写法是加一个上百毫秒的时间锁，
但锁定期内用户的真实滚动会被一起忽略，快速滚动时表现为"另一侧偶尔不跟"。
这里改为记录最近一次程序写入的 `{ 元素, 目标 scrollTop }`：scroll 事件到来时，
若与记录相符就消费掉记录并直接返回；若不符（说明期间用户又滚了）则照常联动。
判据是值而不是时间，因此没有死角。浏览器会把 `scrollTop` 钳制到可滚范围，比较留了 2 px 容差。

**监听器绑在 `#editor-area` 的捕获阶段，全程只绑一次。**
scroll 事件不冒泡，但捕获阶段能收到任意后代的滚动。
于是内核重挂（切标签）、切模式换滚动容器（所见即所得是 `.wysiwyg-host`，源码模式是 textarea）
都不必重新绑定——绑在具体滚动元素上的写法在这两种情况下都会静默失效，
而且失效时看不出任何报错。

**联动只在分屏生效。** 仅编辑区时显示区被 CSS `display: none`，仅预览时编辑区同理；
查看会话（PDF / HTML / 图片）下整个编辑表面被换掉，两者都不该参与。
`syncScroll()` 开头一并挡掉 `state.layout !== 'split'` 与 `viewerSession() !== null`。

**第二问：图标只做两态，不复用菜单的三态循环。**
用户要的是"点一下只剩编辑区、再点一下恢复"。而菜单「视图 → 切换布局」（⇧⌘V）
本来就是 分屏 → 仅编辑 → 仅预览 的三态循环；图标若复用同一条命令，
第二次点击会落到"仅预览"——编辑区消失，与用户预期正好相反。
所以图标走独立命令 `view:toggle-preview`，只在 分屏 ↔ 仅编辑 之间切换，
仅预览仍由菜单到达。命令总线里已有"union 里有、菜单不发"的先例：
`view:zoom-reset`（菜单用的是原生 `role: 'resetZoom'`）。
这条命令**没有加菜单项**：视图菜单已有「切换布局」，再加一项语义重复。

**图标画的是"当前状态"，title 说的是"将要执行的动作"**：

### 再记：预览把含行内标记的列表项拆成多列（2026-10-19 第七轮）

用户发来一张分屏截图，红框圈住一个有序列表项，说：
**"这个预览模式显示的不正确，把 /his-server/api/\*\* 显示错了"**。

截图上编辑区是完整一行
`1. /his-server/api/\*\* 在 SecurityConfig 里没放行——请放行 /api/user/login（以及其余 /api/\*\*）…`，
显示区却把它排成了三窄列并排的碎块，还带着裸露的反斜杠。
两个独立根因同时命中同一行，才有这个画面。

**根因一：flex 容器里每个行内片段都成了一个 flex 项。**
`.md-list-item` 是 `display: flex; gap: 8px`（styles.css:504），本意是"标记 + 内容"两栏；
但 `renderPreview()` 把 `appendInline(item, …)` 的产物**直接挂在 item 上**，
于是文本段、`<code>`、`<strong>` 各自成为 flex 项并排铺开，`gap` 把它们推成几列。
纯文本的列表行只产生一个文本节点，看起来完全正常——
所以这个缺陷只在列表行含行内标记时暴露，而此前受测文档里恰好没有这样的行。

**根因二：`appendInline()` 完全不处理反斜杠转义。**
源码里的 `\*\*` 表示"字面星号"，但行内正则的粗体分支 `\*\*[^*]+\*\*`
会把前后两处 `\*\*` 当成一对来配对，中间那段被塞进 `<strong>`，
而 `textContent` 又原样保留了转义反斜杠。编辑区走 markdown-it，转义被正确还原，
两边因此不一致——这也解释了用户为什么说"预览显示错了"而不是"两边都不对"。

**修复：**

1. 行内内容包进单个 `<span class="md-list-content">`（CSS `flex: 1 1 auto; min-width: 0`）。
   标记与内容仍是两栏，但内容栏内部按行内排版，不再被 flex 拆散。
2. `appendInline()` 加"转义屏蔽"：先把 `\标点` 替换成私有区占位符 `\uE000<序号>\uE001`，
   跑完行内正则，再在写入文本节点与元素文本（含图片 `alt`、链接 `href`）时用 `unshield()` 还原。
   选私有区字符是因为它们不会出现在正常 markdown 里，替换与还原都不会误伤正文。

**为什么六轮自检没抓到：此前没有任何断言看过显示区的 DOM 结构。**
224 项断言里与预览有关的只有"非空""滚动位置保住了"这类外围性质，
列表项的结构和行内文字一次都没被检查过。本轮补 4 条（打包产物上的实测详情）：

- `列表项的行内内容包在单个容器里（不被 flex 拆成多列）` — item 子节点 2 个，内容容器行内元素 2 个
- `列表项文字与源码同义（转义星号是字面字符）` — "/api/\*\* 与 code 和 粗体 在同一行"
- `反斜杠转义在预览中显示为字面字符、不产生强调` — "转义 \*斜体\* 不应倾斜，真代码 仍是代码" em/strong=0
- `真粗体与真斜体仍正常渲染（转义屏蔽没有误伤）` — strong="真粗体" em="真斜体"

第一条断言的是**结构**（`children.length === 2` 且内容在 `:scope > .md-list-content` 里），
不是"看起来对"——正是这个结构决定会不会被拆成多列。

把 `\*斜体\*` 渲染成强调、文字恰好相同也能通过。

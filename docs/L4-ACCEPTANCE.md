## 首要风险已验证闭环：中文 PDF 的字体嵌入

L4 开工前识别的最大风险是"**中文字体在导出 PDF 时的嵌入**"——
字体未嵌入时，PDF 在未安装对应字体的机器上会显示为方框或空白，
而且这个缺陷在开发机上**看不见**（本机装了字体，显示正常）。

验证结果：

| 检查项 | 结果 |
|---|---|
| PDF 文件头合法 | ✅ `%PDF-` |
| **字体数据被嵌入** | ✅ `/FontFile2=true` |
| 文件体积与内容量匹配 | ✅ 72.4 KB（含中文 + 公式 + 表格 + 代码） |

判定依据是 PDF 原始字节里的 `/FontFile2`（TrueType 嵌入字体）标记。
只检查体积是不够的——"导出全是方框的 PDF"体积也不小，
因此断言里同时要求出现字体资源字典与嵌入字体流。

## 本阶段排掉的 5 个真实缺陷

| # | 缺陷 | 根因 | 影响 |
|---|---|---|---|
| 1 | 图片在导出结果里全部不显示 | 导出 HTML 经 `data:` URL 加载，而 `data:` 的源是**不透明来源**，其中 `file://` 与相对路径资源一律被拦 | 导出文档缺图 |
| 2 | 公式在 PDF 里缺字 | KaTeX 的 HTML 输出依赖 20+ 字体文件，相对路径在 `data:` 下同样失效；内联字体又会增加约 1.5 MB | PDF 公式乱码 |
| 3 | 隐藏窗口导出超时 | 隐藏窗口被 Chromium 降频，字体加载与布局迟迟不完成 | 导出挂起 |
| 4 | 大图内联抛错 | `String.fromCharCode(...bytes)` 参数数量超限（数 MB 的图片必然触发） | 导出中断 |
| 5 | 渲染层拿不到干净的二进制 | 主进程返回 `Buffer` 会经 IPC 序列化成 `{type:'Buffer',data:[…]}` 这种 Node 私有形态 | 无法构造 data URL |

### 缺陷 2 的处理最值得记

**导出时把公式的输出从 KaTeX HTML 换成 MathML。**

- KaTeX HTML：排版精细，但依赖 20+ 字体文件、约 1.5 MB
- MathML：**零字体依赖**，Chromium 原生渲染（Chrome 109+ 默认支持 MathML Core）

导出的场景（静态文件、可移植、要打印）里，"零依赖"比"排版精细度略高"重要得多。
所以**编辑器内用 KaTeX HTML、导出用 MathML**，同一份 LaTeX 走两条输出路径。

代价是导出公式的排版细节略逊于编辑器内所见。这是明确的取舍，不是缺陷。

### 缺陷 1 的连锁影响

`data:` URL 的不透明来源不仅拦住 `file://`，也拦住相对路径。
因此"自包含单文件"从"锦上添花的特性"变成了**导出功能的必要条件**：
图片必须内联为 data URL，否则导出结果一定缺图。

## 架构决策

| 决策 | 原因 |
|---|---|
| **隐藏窗口渲染**而非打印当前窗口 | 当前窗口带编辑器 UI，打印它需要大量 `@media print` 特例，且预览与实际输出容易不一致 |
| 导出样式与编辑器样式**分开维护** | 编辑器样式要处理工具栏/光标/选区，导出只关心静态排版与分页；共用一套会让两边都复杂 |
| 字体栈显式包含中文族 | 只写 `serif` 会落到系统无衬线字体，中文纸质输出观感明显更差 |
| 代码块 `break-inside: avoid` | 代码跨页阅读体验极差 |
| 标题 `break-after: avoid` | 避免标题落在页底、正文翻页形成孤行 |
| 明暗与排版分成 `data-theme` / `data-variant` 两轴 | 用户会想要"深色 + 衬线阅读"这类组合，合成单一枚举会组合爆炸 |
| 导出支持传入 `targetPath` 跳过对话框 | 批量导出、CLI 导出、自动化流程都需要；不是为测试加的后门 |

## 已知限制

- 未做 Word/EPUB/PNG 导出
- 导出 PDF 是"渲染后打印"，**不含目录（书签）与页码**——需要额外生成大纲并用 PDF 库写入
- 公式导出排版细节略逊于编辑器内（MathML 取舍，见上）
- 自定义主题是**用户提供的完整 CSS**，不做语法校验；写错只会完全失效，不会崩溃（已用独立 `<style>` 元素隔离）
- 图片缺失时导出为占位文字而非中断（有意选择：让用户看到问题位置）
- 导出固定用浅色配色（PDF 打印不需要深色）
